# Authoritative equipment

## English

The public session owns weapon possession, shared ammunition totals, each weapon's magazine, reload transactions, and shared supply pickups. Client messages contain intentions and server-issued identities, never an ammunition count, pickup quantity, or pickup position. A successful physical shot consumes one round after validation and queue scheduling; pellet count does not multiply ammunition consumption. A cancelled queued shot consumes none.

`EquipmentCatalog.java` is generated by `tools/equipment_metadata.py` from the supported original resources. It records 91 weapon definitions, 28 ammunition types and 56 supported weapon/ammunition/armour pickup definitions. Human on-foot equipment is selected using original weapon flags, groups, animation definitions and human names; animal, vehicle and environment weapon hashes are not an inventory grant. The public-session starting policy grants supported human equipment and seeds each shared `AmmoInfo` pool once to its base `AmmoMaxMP`. Character-stat upgrades to `AmmoMax50MP`/`AmmoMax100MP` are recorded but are not granted by client claims. Reconnecting to the same entity generation preserves consumption. A server-authorized respawn creates a fresh generation and reapplies the starting policy once.

Original default magazine components determine clip capacity. Totals include loaded rounds and are shared by weapons referencing the same ammunition type. Reloading changes the magazine without changing that total. Native `InfiniteAmmo` records remain infinite; thrown weapons consume one inventory item per throw. The original stun-gun clip-size sentinel remains metadata and does not become an invented magazine size.

The supported native flag table identifies bit 16 as `AnimReload` and bit 31 as `UseLoopedReloadAnim`. None of these 91 original weapon records sets the looped flag, including the pump and sawed-off shotguns. Their native `CWeapon::DoReload` therefore uses the full-magazine branch; the `BulletsPerAnimLoop` field alone does not authorize a per-shell loop. This conclusion applies to this pinned resource version.

Native ammunition setters have different side effects. `SET_PED_AMMO` updates the equipped weapon total and preserves its existing magazine only in the `AnimReload` branch when that magazine fits the new total. `SET_AMMO_IN_CLIP` only addresses the currently equipped weapon and also changes the shared pool by the magazine difference. `SET_PED_AMMO_BY_TYPE` writes the pool without changing the equipped magazine. The bridge corrects the selected weapon total, then its magazine, then restores the shared total by ammunition type. Other stored magazines are applied when selected; the bridge does not pretend that the native clip API can update unequipped weapons. `GIVE_WEAPON_TO_PED` creates the inventory item and requests its assets synchronously, while the actual equip/clip operation may need another streaming frame.

Most original `ReloadTimeMP` fields are `-1`, so they cannot supply a guessed delay. The generator follows `weaponanimations.meta` and the default `weaponcomponents.meta` reload definitions into the original `clip_weapons@.rpf` YCD clip map. It validates map counts, pointer ranges, names/hashes, clip types and finite duration fields. The server uses the complete default third-person clip duration divided by the original `AnimReloadRate`, rounded up to a millisecond: pistol/combat pistol 1,834 ms, carbine 2,100 ms, RPG 2,734 ms, for example. These are conservative completion gates, not a reconstruction of the native magazine-insertion animation event or every first-person, cover, skill and animation-rate variation. Client completion must still name the server-issued token and pass that gate. A client cannot complete immediately, supply a duration, add reserve ammunition, replay a completed token, or complete after a weapon switch, death, disconnect or generation change.

Five server-placed supply points around the public spawn use the original pistol, carbine, pump shotgun, RPG and standard armour pickup definitions. They use the original one-metre collection radius, original reward quantities and 60-second regeneration. The authority tests the registered server player position and rejects claims made from a vehicle. A claim consumes one shared pickup generation atomically; the next generation becomes available only after its server timer. A full inventory cannot consume a supply. Armour uses the original 100-point reward and the supported engine's default player maximum of 100, preserving all other combat fields. Native armour reward addition and clamping were checked against `CPickupRewardArmour::Give` and the supported `CPlayerInfo` constructor.

Every operation is fenced by world epoch, entity identity, entity generation and a strictly increasing equipment sequence. Each inventory snapshot includes its own revision and `last_shot_seq`. Individual shot completion/cancellation events remain necessary to retire the client's predicted shots: a maximum sequence does not imply that coalesced or cancelled intermediate shots consumed ammunition. Inventories are private to the owning connection; pickup availability is shared.

The generator pins the original engine and all six resource hashes. Its RPF reader resolves the local engine's archive key in memory and publishes only numeric metadata, never keys or animation members. Original files remain read-only. Java output and optional reports use the shared output guard, fresh temporary files and atomic replacement; external resource roots, source aliases, hard links and symbolic links are protected.

Local verification covers generated-source consistency, original capacities, shared pools, empty magazines, reload conservation and early/duplicate token rejection, monotonically increasing intents, stale generations, reconnect/respawn behavior, thrown ammunition, pickup distance and claim races, regeneration and armour. Output isolation checks verify seven original input hashes before and after. These checks do not constitute rendered game validation.

## 简体中文

公共战局由服务端持有武器所有权、共用弹药总量、各武器弹匣、换弹事务和共享补给点。客户端只能发送意图与服务端发出的身份标识，不能授权弹量、拾取奖励数量或拾取物位置。射击通过验证并真正出队击发时才扣一发；霰弹的多颗弹丸不重复扣弹，取消的排队射击不扣弹。

`EquipmentCatalog.java` 由 `tools/equipment_metadata.py` 从受支持的原资源生成，记录 91 个武器定义、28 个弹药类型和 56 种已支持的武器、弹药、护甲拾取定义。初始公共战局装备策略依据原武器标志、分组、动画定义和人类武器名称授予受支持的手持装备；动物、载具和环境伤害哈希不作为个人武器发放。每个共用 `AmmoInfo` 池只初始化一次原版基础 `AmmoMaxMP`，不接受客户端自报技能来增加上限。50/100 技能的原上限被记录但不自动授予。同一实体代次重连保留消耗；服务端确认重生后，新代次仅应用一次初始装备策略。

弹匣容量取原默认弹匣组件。总弹量包含已装填子弹，同弹药类型武器共享总量；换弹只改变弹匣，不增加总量。原版无限弹药标志与投掷物逐枚消耗被保留，电击枪原始弹匣哨兵数值不会被替换成自创容量。

原引擎武器标志表已确认 bit 16 为 `AnimReload`，bit 31 为 `UseLoopedReloadAnim`；本次固定资源的 91 项武器均未设置后者，泵动和短管霰弹也不例外，因此原 `CWeapon::DoReload` 走整匣分支。仅有 `BulletsPerAnimLoop` 字段不能证明当前资源启用了逐发装填，这一结论仅适用于已固定版本。

原生弹药接口的副作用不同：`SET_PED_AMMO` 会更新当前武器总量，只有 `AnimReload` 且旧弹匣不大于新总量时保留旧弹匣；`SET_AMMO_IN_CLIP` 只作用于当前装备武器，并按弹匣差值改变共享池；`SET_PED_AMMO_BY_TYPE` 只改弹药池而不改当前弹匣。因此客户端按当前武器总量、当前弹匣、按类型恢复共享总量的顺序校正，未装备武器的服务端弹匣等切换后再应用。`GIVE_WEAPON_TO_PED` 同步创建库存项并请求资源，但实际装备和弹匣接口可能需等待后续流式加载帧。

原步行 `ReloadTimeMP` 大多为 `-1`，不能猜测换弹时间。生成器沿原 `weaponanimations.meta`、默认 `weaponcomponents.meta` 装填定义读取 `clip_weapons@.rpf` 的 YCD 片段表，验证数量、指针、名称/哈希、片段类型和有限时长。服务端以完整默认第三人称片段时长除以原 `AnimReloadRate`，向上取整为毫秒作为完成门槛，例如手枪/战斗手枪 1,834 毫秒、卡宾枪 2,100 毫秒、RPG 2,734 毫秒。这是保守的完成门槛，尚不等同于原生插匣动画事件帧，也未重建全部第一人称、掩体、技能和动画倍率分支。原生完成通知还必须携带服务端令牌并通过此门槛。立即完成、自报时长、增加备用弹药、重复令牌、切枪/死亡/断线/换代后的旧完成消息均不能加弹。

出生点周边五个服务端补给点使用原手枪、卡宾枪、泵动霰弹、RPG 和标准护甲定义，沿用原一米收集半径、奖励数量及 60 秒再生时间。距离取服务端已登记的角色位置，并要求下车领取；领取事务原子消耗当前共享拾取代次，计时结束才产生下一代。容量已满不能消耗补给。护甲按原 100 点奖励相加，再限制到已核验原引擎默认玩家上限 100，保留其他战斗字段；对应原版 `CPickupRewardArmour::Give` 与 `CPlayerInfo` 构造函数已做静态核对。

每条装备操作校验世界 epoch、角色身份、实体代次和严格递增序号。库存快照含独立 revision 与 `last_shot_seq`；客户端仍需逐条终结射击完成/取消状态，不能把最大序号误当作中间取消事件均已扣弹。库存只发给本人，拾取可用状态共享。

生成器固定原引擎及六份资源的哈希，归档密钥仅从本地匹配引擎在内存中解析，不输出密钥、动画成员或原资源。生成源码和可选报告使用统一输出保护、独立临时文件与原子替换，覆盖外部资源目录、源文件别名、硬链接和符号链接。原输入始终只读。

本地检查覆盖生成一致性、原容量、共用弹药、空弹匣、装填守恒与过早/重复令牌拒绝、序号与代次、重连/重生、投掷扣弹、拾取距离/竞态/再生和护甲；输出隔离检查核对七份原输入前后哈希不变。这些检查不等同于实机画面验证。
