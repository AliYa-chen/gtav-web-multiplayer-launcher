# 角色同步接口静态审计

审计日期：2026-10-07。检查对象为 `gta5data/b/8b0b5899ed/game.wasm`、`game.js` 和 `client/loader.js`。只解析了 WebAssembly 的 name、type、import、function、export 节及 JavaScript 文本；没有运行游戏、调用内部函数或修改引擎二进制。

## 当前结论

引擎二进制保留了创建角色、创建车辆、读取位置、修改位置和生命值的内部脚本命令。这提供了进一步研发真实同步的入口线索，但项目目前没有把这些命令作为可用的 JavaScript 接口公开。大厅 WebSocket 成功连接、房间成员变化或收到启动通知，都不能证明游戏里的角色已经同步。

该 WASM 为 63,201,802 字节，有 91,111 个函数索引，name 节也记录了 91,111 个函数名称。export 节只公开了 20 个不同的函数索引，共 21 个函数导出名称；其中 `htons` 和 `ntohs` 共用同一函数。函数导出均属于主入口、线程、异常或栈等运行时功能，下面列出的游戏命令均没有导出。

`GET_ENTITY_COORDS` 的名称只有两个显式 C++ 参数，WASM 却有三个参数并无返回值。后续函数体解码确认，第一个 `i64` 是返回结果地址：它在该地址的偏移 `0`、`8`、`16` 分别写入 `f32`。`CREATE_PED`、`CREATE_VEHICLE` 和坐标写入函数也从 `scrVector` 地址的这三个偏移读取 `f32`。因此这里的向量数据不是三个连续的四字节浮点数。

对应脚本包装器也存在，例如 `CREATE_PED` 为 57729、`CREATE_VEHICLE` 为 62000、`GET_PLAYER_PED` 为 58866、`GET_ENTITY_COORDS` 为 50221、`SET_ENTITY_COORDS` 为 50325、`GET_ENTITY_HEALTH` 为 50227、`SET_ENTITY_HEALTH` 为 50330。它们统一为 `(i64) → void`，名称中的实参是 `rage::scrThread::Info&`。name 节中没有匹配到 `scrNativeCallContext` 符号；这不证明引擎不存在相应结构，仅说明不能套用别的 GTA native 调用库的对象布局。

## JavaScript 和执行线程的限制

`game.js` 中没有 `ccall`、`cwrap`、`addFunction`、`dynCall` 或明确的 native 调用桥。`assignWasmExports` 绑定了现有运行时导出；`wasmExports` 与 `getWasmTableEntry` 是脚本内部变量。`__indirect_function_table` 虽然被导出，但其表索引与函数索引不同，不能拿上表编号直接调用 `wasmTable.get(...)`。

`loader.js` 通过 `importScripts` 在引擎 Worker 内启动 `game.js`。页面线程的 WebSocket 回调无法直接在引擎当前游戏帧或脚本线程中调用实体命令。即使新增导出，还必须确认正确的线程、游戏状态和调度时点，并实现把网络消息送进引擎执行队列的桥。现有 `keepThreads` 位掩码还控制重播、网络和视频线程；仅恢复网络线程不能自动兼容一个新写的 Java 大厅协议。

## 函数体解码后的补充证据

`tools/inspect_native_bridge.py` 可以复现函数索引、签名、导出、准确的指令偏移、直接调用和内存操作审计；生成记录位于 `docs/snapshot/native-bridge-evidence.json`。工具会在不支持的指令处停止并标记未完成，避免把猜测字节当作调用；本次默认选择的目标函数均完整解码。

`Main_OneLoopIteration()` 为函数 106，函数体只有 86 字节，最终调用 `rage::fwFsm::Update()`，自身没有安装活动脚本线程。现有 JavaScript 导入 `env.wasm_module_int_js` 为函数索引 11，签名是 `(i64, i32) → i32`；理论上可在独立实验副本中复用这个导入回调而不新增导入、不改变函数索引，但本次没有制作或运行该补丁。

`GetActiveThread()` 的函数体从 `global 1 + 3088` 读取活动脚本线程地址。创建角色最终调用 `CTheScripts::RegisterEntity()`；该函数在取得活动线程后直接读取 `thread + 560` 的脚本 handler，没有对空活动线程做检查。模型请求同样多次依赖活动脚本线程和当前 handler。坐标写入也不能简单放到主循环头执行：`SetEntityCoords → SetEntityCoordsExt → CScriptPeds::SetPedCoordinates` 的一个游戏状态分支会在活动线程上直接读取偏移 36，并登记其偏移 428 的引用。

这意味着“在引擎主线程调用”仍不足以保证写入命令安全。还要进入或建立有效的脚本上下文，处理实体与脚本资源归属、线程状态的恢复以及异常退出。伪造 handler 指针或只修改 TLS 的某个地址，尚无运行期验证，不能作为可交付方案。

较小的第一步是只读验证：`CommandGetPlayerPed(-1)` 在该构建中确有本地玩家分支，取得角色后可读坐标与生命值。玩家对象生命周期、远程角色创建、伤害和载具同步属于独立的适配环节。

## 真正联机需要验证的下一步

1. 在独立实验中建立引擎 Worker 内的调用与调度桥，先可靠读取本地玩家角色、坐标和生命值，再证明退出或重新加载时不会使用失效句柄。
2. 确认实体句柄与 `scrVector` ABI、模型预载和角色生命周期，验证创建第二个游戏内角色与更新位置。函数索引或导出补丁本身不构成验证结果。
3. 对不同客户端维护独立的实体句柄映射，加入状态快照、插值、断线销毁和重生流程。
4. 为射击、伤害、死亡和车辆控制定义同步与归属规则；仅广播生命值或位置不足以处理命中、座位、物理碰撞和载具控制权。
5. 统一两端角色状态、伤害结果与共同车辆操作，分别维护每端实体句柄。

Java 服务端可以继续只处理会话与同步消息，不必存放或渲染游戏资源。但如果需要可信的命中与物理判定，就必须明确服务器或房主如何验证这些结果，而不能把任意客户端发来的消息直接当作事实。
