# 原生网络复制可行性审计

审计日期：2026-10-08。对象是原始 `gta5data/b/8b0b5899ed/game.wasm`，63,201,802 字节，SHA256 为 `11ca8d2c04c5e843d18ff4aea4899d72c86973c6b031df334e67c446b2ae83e0`。本次没有实例化 WASM、修改引擎或构建运行副本，没有连接官方服务。检查了 139 个选定函数的完整指令边界、实际 ABI、直接调用和虚调用位置，并静态读取 data/element 节。

## 结论与研发方向

**当前构建确实保留了通用的网络对象复制、数据树编解码、任务复制、载具状态复制、控制权迁移和游戏事件通道。它们有实质函数体及相互连接的调用路径，不只是名称残留。** 因此，继续把每一种动作重新定义为一个 JSON 字段和 native 命令，并不是实现大范围共享世界的唯一方向。值得把研发重点转到原生 clone/sync tree 的通用传输与会话适配。

同时，本次证据不能证明只给 Java 增加一个二进制 WebSocket 端点就能开启 GTA Online。原 peer socket 的绑定、发送和接收有明确空实现；网络对象创建、应用数据树和任务复制仍要求真实的本地网络管理器、玩家对象、对象 ID、脚本 handler、模型资源和帧调度。原身份/匹配入口也不能用当前房间 UUID 直接替换。

较合适的目标是：**自有公共战局身份与控制权服务，客户端尽量复用原生实体/任务/物理复制，Java 维护公共对象目录、控制权、快照和重要事件裁决。** 原始二进制内容可以通过 WS/WSS 传输；更换传输协议不会自动初始化游戏网络环境。服务端可以不渲染游戏和不存放资源，但若完全不解析状态、不具备碰撞信息，只能做到经权限约束的复制与事件仲裁，不能承诺所有命中、物理和 AI 都由 Java 独立模拟。

本报告给出适配边界与验证次序，不把这些静态发现称为已完成联机。

### 具体编解码入口可静态确认

此 WASM 的 4077 个 data segment 是 passive 段。通过 `__wasm_init_memory`（88）中的常量 `memory.init`，可把线性内存地址映射回文件内容；不需要运行 WASM。Element 段给出间接表槽位到函数索引的映射。

`WriteData` 实际使用的 writer vtable 线性地址是 `4278080`，reader 是 `4278552`。例如：

| 方法槽偏移 | writer / 原函数 | reader / 原函数 | 静态文件中槽位字节位置 |
| ---: | --- | --- | --- |
| +64 | table 7043 → 8135 `CSyncDataWriter::SerialiseBool` | table 7071 → 8200 `CSyncDataReader::SerialiseBool` | 52824540 / 52825012 |
| +112 | table 7049 → 8134 `SerialiseUnsigned(unsigned short&,int,...)` | table 7077 → 8199 同字段 reader | 52824588 / 52825060 |
| +136 | table 7052 → 8617 `SerialisePackedFloat` | table 7080 → 8639 对应 reader | 52824612 / 52825084 |
| +152 | table 7054 → 8136 `SerialiseObjectID` | table 7082 → 8202 对应 reader | 52824628 / 52825100 |

8134/8199 分别调用 `datBitBuffer::WriteUnsigned` 1141 / `ReadUnsigned` 1140，并推进位游标。writer/reader 是真实位编码。基础类的某些默认实现只有 `end`（如 SerialiseDataBlock 7998、ActivationFlags 8577/8578），不能把它们误当作整个具体复制系统被移除。

已确认的 `datBitBuffer` 局部布局：数据指针为 `+0` 的 i64；初始位偏移 `+8`、位容量 `+12`、当前游标 `+16`、最高写入游标 `+20`、其它标记 `+24/+28`。1148 `SetReadWriteBytes(ptr,len)` 把 len 左移 3 写为位容量；1149 `GetNumBytesWritten` 使用 `(+20 + 7) >> 3`。这足以构造后续受控的原生编解码探针，**还不足以手工拼造合法的整个网络对象或 reader/target**。

## 3. 传输与会话仍有明确缺口

当前路径大体为：

```text
原生 netObject / sync tree
  → CloneCreate / CloneSync / ACK 打包
  → netPlayerMgrBase::SendBuffer (7780)
  → netConnectionManager::Send (13550)
  → 连接发送队列及 Send() (13454)
  → SendPacket (13457)：含 P2pEncrypt、relay/peer 路由
  → netSocketManager::Send (13536)
  → netSocket::Send (13571)：真实 peer 发送缺失
```

7780 的实际 ABI 为 `(i64,i64,i64,i32,i32,i64,i64) → i32`；13550 为 `(i64,i32,i64,i32,i32,i64) → i32`。它们操作的是**已经存在的 netPlayer、connection、buffer**。导出 7780 不能把一段 JSON 当作树数据，导出 13550 也不能把 Java 分配的连接 ID 当作原 connection 对象。

8160 `SendPackedReliableMessage`、8161 `SendConnectionSyncMessage`、8159 `SendPackedSyncAckMessage` 都是真实构造原 header/bit buffer 后调用 7780。接收方 8197 `netObjectMgrMessageHandler::OnMessageReceived`（6905 字节）解析 packed 消息、object ID、节点位数、create/sync/remove/ack 分支，并有具体对象管理器虚分派。可靠性、丢包 ACK 和迁移队列已经在引擎内存在；只广播裸对象数据会丢掉这些上下文。

原 socket 缺口已重新核对：

| 函数 | 索引 / 文件体偏移 | 精确证据 |
| --- | --- | --- |
| `netSocket::GetLastSocketError()` | 181 / 1470206 | 完整体 `00 41 01 0b`，始终返回 1。 |
| `NativeBind()` | 185 / 1470249 | 尾段写对象 handle `+8=-1`，返回 0；没有 socket 创建/绑定调用。 |
| `NativeGetReceiveBufferQueueLength(unsigned int&)` | 186 / 1470337 | 完整体 `00 20 01 41 00 36 02 00 41 00 0b`，写 0 并返回 0。 |
| `NativeGetPortRangeForRandomSelection` | 187 / 1470349 | 完整体 `00 20 00 41 00 3b 01 00 20 01 41 00 3b 01 00 0b`，两个端口均写 0。 |
| `netSocket::Send(...)` | 13571 / 7633632，624 字节 | 完整解码的直接调用没有 `send/sendto`、syscall 或 JS 网络桥，没有间接调用；仅就绪检查、临界区、包尺寸与统计等。 |
| `netSocket::Receive(...)` | 13829 / 7839343，3110 字节 | 7840045 的 `i32.const -1` 以及 7840049 的恒真分支跳过原接收块；剩余模拟/延迟队列等不能从真实网络收包。唯一间接调用是 packet recorder。 |

原生 TCP/TLS 库和浏览器 Emscripten socket 胶水仍存在，但它们不自动补足这条 peer transport。更多详细证据见 [原线上模式审计](原线上模式审计.md)。

### 原网络脚本不是普通单机线程上的一个布尔值

`NETWORK_SET_THIS_SCRIPT_IS_NETWORK_SCRIPT`（54840，2376 字节）与 TRY 入口（54841，79 字节）真实存在。54841 调当前活动线程和 `CGameScriptHandlerMgr::TryToSetScriptAsANetworkScript`（64228，1471 字节），成功后才取 `CGameScriptHandlerNetwork` 并设置参与者数。54842 的 9 字节函数直接检查该 network handler 是否存在。

`NETWORK_IS_SESSION_ACTIVE`（54707）转到 `NetworkInterface::IsInSession`；`IS_SESSION_STARTED`（54708）转到 `IsSessionEstablished`。原 host 入口 54639 先调用 54628 的多人访问检查，再到 83078 和 85824。`CNetwork::CheckNetworkAccess`（82940，2991 字节）实际检查 sign-in、online、ROS credentials/privileges、多人禁用和 cloud scripts。

这些是两类不同问题：自有 clone channel 可以研究自己的会话/handler 初始化；复用整个原 GTA Online 开始流程则会进入原匹配和访问体系。不能因导出了某个 network native，就假设所有前置条件已满足；也不能把所有实体树入口都误说成每次会直接访问 ROS。

## 4. 迁移和游戏事件是共享世界的一部分

控制权逻辑仍有实质实现：8102 `netObject::CanPassControl`（336 字节）、8104 `CanAcceptControl`（274 字节）、8166 `netObjectMgrBase::ChangeOwner`（1805 字节）。8166 会调整本地/远端对象队列、树批次、节点发送状态和同步消息队列。`CGiveControlEvent::Prepare/Handle` 为 89344/89345，596/762 字节，包含对象 ID 和迁移类型序列化；对象迁移不能等价成只换一个 owner 字符串。

玩家抢 NPC 的车，需要统一的 ped/vehicle 对象 ID、座位和占用关系、唯一模拟拥有者，以及状态和控制权转换。每个客户端继续独立生成同一区域随机 NPC/交通，仅同步玩家，仍会形成不同世界。通用复制应让服务器指定区域/对象的模拟 owner，其他客户端接收克隆；owner 离开后重新分配，完整快照和 delete 消息清理失效对象。原生人口/作用域管理器可以研究复用，但本次尚未初始化或验证。

**只接 clone/sync 树也不覆盖所有瞬时事件。** 另外存在通用原生事件通道：

| 事件/管理器 | 原索引 / 函数体字节数 | 已确认内容 |
| --- | --- | --- |
| `netEventMgr::PrepareEvent` / `OnMessageReceived` | 7849 / 1805、7935 / 4688 | 事件构造、收到事件、可靠性与分派。 |
| `netEventMgr::SendPackedEventsMessage` / `SendPackedEventReliablesMessage` | 7938 / 480、7939 / 636 | 原事件消息打包。 |
| `CWeaponDamageEvent::Prepare` / `Handle` | 89364 / 2961、89365 / 3117 | 位流、武器/对象 ID、浮点与布尔字段。 |
| `CExplosionEvent::Prepare` / `Handle` | 89475 / 2329、89476 / 2526 | 原爆炸事件编解码。 |

这允许研究通用事件转发与服务器准入，而不必把每次射击还原成一个新 Task 命令。服务端仍须限制来源、对象 owner、序号、事件种类和字段范围；若它仅原样转发不可见的原包，不能声称伤害、击杀和物理已由服务器权威裁决。

### 中心 AI/物理事件观察入口：能扩大覆盖，但不是通用重放 API

还有独立于 `netGameEvent` 的本地 `rage::fwEvent` 体系。以下位置比逐个近战、逮捕、上车命令更适合调查“引擎实际发生了什么”：

| 入口 | 索引 / 体偏移 / 字节数 | ABI 与已验证布局 |
| --- | --- | --- |
| `CEventGroupPed::Add(rage::fwEvent const&)` | 30722 / 19105357 / 1433 | `(i64 group,i64 event) → i64`；从 group `+152` 读取 owner 指针，再读取 owner `+4320` 并调用 `CPedIntelligence::RecordEventForScript`，佐证此字段是 ped owner。 |
| `CEventGroupVehicle::Add(rage::fwEvent const&)` | 30732 / 19110051 / 1185 | 同 ABI；group `+56` 为 owner 引用，后续读取其 entity/network 状态并经虚接口验证。该指针的运行时 vtable/type 仍应核对，不能假设总是存活的车。 |
| `CEventGroupGlobal::Add(rage::fwEvent const&)` | 30734 / 19111937 / 309 | 同 ABI；没有 per-ped/per-vehicle owner 字段，使用全局队列。 |
| `CEventHandler::GetCurrentEventType() const` | 30763 / 19118955 / 59 | `(i64 handler) → i32`；先检查 handler `+24`、`+16`、`+40` 的事件指针，选中后调用 event vtable `+32`，均为空返回 -1。 |

实际 vtable 例子：`CEventDamage` 构造器把 vtable 地址 `4831328` 写入 event `+0`；该表 `+32` 映射到函数 11648，函数体只有 `i32.const 17; end`，即 damage 事件 type 17。name 节给此函数的名称却是 `rage::cutfDecalObject::GetType() const`，是相同常量函数合并后的共享函数名称。这说明虚调用应核对**表槽和实际体**，不能只按符号名称判断归属。

三个 Add 都调用 `NetworkInterface::OnAIEventAdded`（83174）。该函数先检查网络标记，再按 event type 分支；可见分支含枪弹擦过/消音枪声相关通知。它是已存在的 AI 到网络事件适配点，但没有把任意 `fwEvent` 编码成通用 payload，不能把它解释成“接管此函数即可转发全部游戏事件”。

可以研究在这些中心 Add 点同步记录一个固定容量观测 ring：event type、owner 的稳定全局映射 ID、发生帧/时间和经过明确布局核对的可复制字段。主引擎线程下一安全帧读 ring，再发布给自有复制层。这个方案用于了解事件覆盖、发现需要走原 netGameEvent 的情况，不能靠只复制 type 让另一端出现同样效果。

安全调用边界也具体存在：Add 内部使用临界区、克隆/删除事件、操作各自容量为 16/4/32 的队列，调用者可能是游戏/AI/物理路径，不能假设已有 scrThread TLS。hook 不应在持锁路径发 WS、调用实体 native、分配大量 JS 对象或把异常抛回 WASM。原 event/owner 指针只能在有效调用内观察；异步排队 raw pointer 会在对象销毁后失效。应同步复制固定数据到预分配 ring，事件丢弃/替换也须记录，不能把函数入口的“尝试 Add”都称为最终被接受的游戏结果。本次没有插入此 hook，也未验证全部事件都会经过这三个入口。

### `RetrieveData` 是本地脚本 ABI，不是统一网络序列化

`CEventNetworkWithData<T,N,D>::RetrieveData(unsigned char*,unsigned int)` 有统一的 `(i64 event,i64 out,i32 length) → i32` 形式，但模板的 D 布局并不相同。例如：

- EntityDamage 模板 30917 要求 length **等于 104**，从 event `+32` 复制 104 字节。
- ScriptEvent 模板 32100 要求 length **等于 432**，从 event `+25` 复制；派生类 override 31571 允许小于 433 的长度。
- PlayerCollectedPickup 模板 32008 要求 length **等于 48**，以 SIMD 分段复制。

部分实现复制前调用 event vtable `+88`，也会生成诊断文字；“const 方法”不能被当作完全无副作用的内存拷贝。派生的 `CEventNetworkEntityDamage::RetrieveData`（30916）还先读取 event `+136/+144` 的本地 CEntity 引用，通过 `fwScriptGuid::CreateGuidFromBase`（8689）写成本机脚本 GUID，再复制 104 字节。**这些 GUID 在另一客户端没有相同含义。** 普通 `CEventDamage` 的构造器 30828 把原 CEntity* 保存于 event `+48` 并建立 `fwKnownRefHolder`；CloneEditable 30831 保留引用，GetSourceEntity 30836 返回原生实体指针，整段结构更不能跨进程传递。

因此，通用 `RetrieveData` 有利于单客户端脚本观测和字段审计；未取得每种数据的尺寸/引用 schema 前，不适合把输出 blob 发给另一客户端。真正能作为 wire 接入候选的仍是上表 `netEventMgr` 和 `CWeaponDamageEvent`、`CExplosionEvent` 等原 prepare/handle 位编码。两套事件类型编号、对象生命周期和消息语义必须分别维护，不能混用。

## 5. 可以补导出，但先证明调用对象有效

没有源代码也可在独立副本增加 export：当前构建器已证明能保持原函数索引、导入、type、data、element 节，并把选定原函数公开。JS 可以通过 WASM memory 复制位流，然后使用准确 ABI 调用原编解码器。这是可行的工具能力，不是运行前置条件的替代。

适合优先验证的少量通用入口是：树 getter/状态观察、`datBitBuffer` 32 字节构造与 bind、已有 node 的 WriteData/ReadData、tree Write/Read、clone create/sync/delete、event dispatch。**不应先给几十个交互增加单独导出，再把它们当作通用网络层。** `GetCurrentGtaScriptHandler` 与 `GetCurrentGtaScriptHandlerNetwork` 的区别、netPlayer 的初始化、native object allocator、模型加载和目标 accessor 的合法性都必须得到实测证据。

不建议对任意单机 ped 直接调用 tree Apply、伪造一个 vtable，或把 raw handle 作为跨客户端 ID。引擎网络对象和具体实体引用有生命周期；JS callback 必须交给正确线程/帧点执行，不能在页线程 WS onmessage 中直接操作脚本对象。现有 scrThread hook 是脚本 native 的可控调度点，但网络管理器还有独立锁和网络阶段，不能假设同一 hook 对所有 network 方法都适用。

### 建议验证顺序与停止条件

1. **复制层可调用证明**：在隔离副本读取网络管理器/树是否初始化；找到真实 local player/ped 的合法 target object，把一个原节点编码到自有 bit buffer。验证位数/边界，不创建假的网络指针。若单机启动下对象始终为空，应先解决最小自有 network context。
2. **原树往返证明**：在同一客户端以合法目标进行编码、解码和受控应用，核对模型、位置、外观、任务数据；确认不会改变原单机资源及跨线程 TLS。
3. **两个客户端原生 clone 证明**：自有 Java 房间发放版本、全局对象 ID、owner/epoch；仅一个玩家 clone，再验证创建、更新、删除、重连恢复。WS/WSS 承载二进制，Java 不把本地 C++ 指针转给对方。
4. **NPC/载具/迁移证明**：一个 owner 创建 ped/vehicle、其他客户端接收相同对象；验证玩家上车、抢车、座位占用和 owner 离开。其他端本地随机世界对象需要控制，避免同位置的重复车和 NPC。
5. **通用事件与权威规则**：对伤害、死亡、爆炸和控制权事件定义服务端批准/拒绝；复用原 prepare/handle，限制事件类别，加入断线快照与过期 epoch。
6. **玩法一致性**：近距离战斗、NPC 交互、驾驶/乘客、车辆死亡、区域流式加载和 owner 离开后接管共用实体生命周期与所有权规则。

这条路线降低逐动作重写的长期成本，但前几个阶段可能发现该移植缺少可独立初始化的关键上下文，或者某些原状态节点不能安全接入离线 world。此时应据实报告那个具体边界，再选择有限的自有 entity layer；不能从符号多或能成功编译推导全面兼容。

## 复核记录与范围

本地详细记录保存在 `docs/snapshot/native-network-clone-evidence.json`，包含各函数的 name/type、体偏移/字节数/SHA256、准确调用位置、静态标签和 writer/reader 表映射；该目录沿用项目规则忽略 Git，不包含服务端密码。报告本身可进入源码仓库。基本函数体证据可用现有工具复核，例如：

```sh
python3 -B tools/inspect_native_bridge.py --match 'netSyncTree::|ProcessCloneCreateData|ProcessCloneSync|CPedMovementDataNode::Serialise|CVehicleControlDataNode::Serialise' --output docs/snapshot/native-clone-functions.json
```

静态表映射方法为：读取 passive data segment；解析函数 88 的常量 `memory.init(dest,source,length)`；再解析 element 段的 table 初始偏移与函数索引列表；按 vtable 地址读取 little-endian uint64 槽位。`4278080+136` → 槽 7052 → 原函数 8617 是一个明确复核点。所有文件偏移以本报告开头的原引擎 hash 为准，公共副本偏移不能直接套用。

本次证明的是原代码保留程度、编码/应用路径和适配边界。未完成原包协议全覆盖、未恢复 socket、未初始化原网络游戏、未以该树驱动两个客户端，也没有重建官方票据或商城/云服务。
