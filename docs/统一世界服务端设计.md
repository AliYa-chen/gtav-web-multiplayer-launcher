# GTA V 公共战局的统一世界服务端设计

研究日期：2026-10-08（上海时间）。本文给出整体改造设计与只读审计证据；完整统一实体协议及原生复制尚未实现，没有连接官方服务。

设计完成后，项目已加入 Java `0.2.5-public` 的 `WorldRegistry` 与 `WorldProjection`：前者实现统一 ID、组件、租约、版本、原子座位事务和快照；后者只把 `CombatWorld` 已确认的玩家结果纳入统一视图，`GET /world` 可读取一致切面。完整 NPC／车辆世界与原生 clone 仍未接通，返回值明确标记 `shared_population=false`、`native_clone_transport=false`。客户端只读观测同步树与网络脚本上下文的初始化状态，不把静态符号存在当作可用网络对象。

## 当前实施进度

隔离的 `0.3.0-world-experimental` 已将 `WorldService` 和 `WorldRegistry` 作为唯一实体事实，移除广播后的 `WorldProjection` 镜像。v1 玩家输入、v2 实体批输入、战斗、座位、生命候选和重生均进入同一世界；快照和增量带 epoch、版本、代际、scope 与连续流序号。

客户端已接入组件路线的角色、车辆、乘员和区域人口适配，服务器下发固定目录并分配模拟租约；同一批姿态更新包含附座实体，NPC 抢车使用三实体原子事务。近战由服务器按距离、方向与冷却判定；环境与被捕状态仍是受所有权约束的候选报告，不能称为 Java 独立执行 GTA AI、导航或物理。

原生复制的运行态证明仍没有有效日志，未调用未验证网络对象；`native_clone_transport=false` 与 `game_sync=false` 保留。当前开发测试已按用户要求将 47485 和 47486 一并更新 0.3.1，仍保留回滚副本。

## 方向与真实边界

建议把现有的“玩家列表加射击转发”改为一个公共世界：玩家、NPC、车辆和物件都由服务端分配身份、登记生命周期、裁决归属、保存版本化状态，并通过统一快照和增量分发给客户端。战局仍只有一个 `PUBLIC`，地图固定 GTA V 沙盒。这能解决同一车辆或 NPC 在两台机器上变成不同对象、离开后重复生成、死亡和重生互相覆盖等结构性问题。

服务端的登记和裁决，不等于服务端已能执行 GTA 的所有物理与 AI。目前 Java 既没有 RAGE 仿真，也没有加载地图碰撞。可落地的第一条路线是：Java 决定世界事实与模拟租约，指定客户端的 GTA 引擎计算某个实体或区域的移动、车辆物理和 NPC 行为，其他客户端只应用确认状态。移动、射击和生命周期仍由服务器验证并提交。这属于客户端参与仿真的自有同步世界；涉及碰撞或 AI 的上报只具有有限验证能力，不能称为完整物理权威。

若要求载具碰撞、墙体遮挡、行人 AI 等重要结果完全由服务器独立重算，必须另外具备可运行的服务器仿真：适配成无图形依赖的引擎，或实现兼容的碰撞、导航与物理运行时。把 `.meta`、`.rpf` 或 `game.wasm` 复制到服务器目录，不能自动获得这些能力。

### 游戏数据能提供什么

当前文件中可直接读取 `common/data/levels/gta5/vehicles.meta` 的 298 个 `modelName`、`common/data/handling.meta` 的 248 个 `handlingName`，以及人口、场景和武器配置。它们可用于生成版本固定的车型／模型目录、座位布局线索、规则白名单和资源指纹。

数据目录还包含 1528 个 `.rpf`、470 个 `.ymt`、376 个 `.meta`。这次目录扫描没有发现独立的 `.ybn/.ymap/.ynd/.ynv`，但这些资源可能在归档或其它格式中；不能因此判定碰撞与导航资源缺失。反过来，即使资源存在，也需要可靠解包、格式解析、变换及运行算法，才可用于 Java 的服务器碰撞或导航。`handling.meta` 中质量、悬挂和牵引参数本身不是一套车辆物理实现。

统一协议应协商 `build_id` 和资源目录摘要，而不是假设所有 GTA 版本的模型和 native 相同。服务器可只部署小型规则目录，游戏模型、贴图和地图仍由客户端加载；若将来实现权威地图判定，则服务器还需要相应碰撞和导航数据。

## 统一实体与组件

建立 `WorldRegistry`，将会话身份、世界实体和本机 native 句柄拆开：

- `player_id`：连接恢复后保持的玩家身份，和 WebSocket socket 分离。
- `entity_id`：由服务器创建的世界对象身份，类型可以是 `ped`、`vehicle`、`object`；同模型和同坐标不能作为身份。
- 本地 `handle`：每个客户端维护 `entity_id → native handle`，不向服务器或其它客户端发送该句柄；重新创建本地副本不改变世界身份。

实体 ID 使用字符串，例如 `w:<world_epoch>:<counter>`。`counter` 在同一世界中不复用，避免 JavaScript 64 位数精度及删除后旧包误命中。`world_epoch` 在服务器世界重建时改变；旧世界的恢复身份和输入必须被明确拒绝。角色重生可保留原世界身份并更新 `life_generation`；更换本机 ped 句柄不能被当成另一个玩家。

建议的实体记录：

```json
{
  "entity_id": "w:e3:81",
  "kind": "vehicle",
  "model": 1032823388,
  "revision": 19,
  "life_generation": 1,
  "owner_id": "玩家身份",
  "owner_epoch": 4,
  "lease_until_tick": 2600,
  "components": {
    "transform": {
      "position": [711.5, -1088.1, 22.4],
      "rotation": [0.0, 0.0, 0.0, 1.0],
      "velocity": [0.0, 0.0, 0.0]
    },
    "vehicle": {
      "engine_health": 1000,
      "body_health": 1000,
      "seats": {"driver": null, "passenger:0": null}
    }
  }
}
```

这是协议形状示例，模型与数值不构成当前支持车型或车辆实现。姿态四元数、角速度、门窗、损伤、任务等具体字段，必须按对应引擎适配器验证后加入组件 schema；服务器严格限制大小、数值及可写字段，不能接收无限制的任意 JSON 组件。

核心组件分为：`transform`、`appearance`、`combat`、`ped_actions`、`vehicle`、`attachment`、`simulation_task`。生命周期、所有权、创建与删除使用共同机制；每种组件仍需要正确的采样／应用适配器。统一注册表可以消除重复生命周期代码，不能省略车辆座位、物件挂接等本来不同的语义。

## 服务器权威与仿真所有权

**服务器始终裁决**：对象是否存在、实体 ID、创建／删除权限、所有者租约、玩家身份、座位占用、战斗血量、分数、死亡重生、全局时间／天气政策、已验证状态的提交和版本。请求进入车辆时，服务器原子判断距离和空座位，再提交 occupant 变更；不能让两个客户端各自抢到驾驶位。

**仿真客户端暂时代算**：其租约范围内的车辆运动、NPC 导航与任务、物理接触的候选结果。服务器校验 sender、`owner_epoch`、输入序号、速度和范围，然后决定是否提交。客户端依然负责输入、模型流式加载、画面插值和原生引擎应用。

普通玩家可以提议自己的移动，不能写其它实体；驾驶员获得车辆运动租约，乘客不能写车辆姿态；NPC 按区域分配给指定模拟者。一个实体某一时刻只有一个有权提交动态状态的模拟者。所有客户端都保留同一确认状态，非模拟者不得让本地 AI、伤害或物理结果自行变成世界事实。

现有单机环境会各自在附近生成 NPC 和车辆。它们没有共同身份，不能简单把所有本机附近句柄都登记成公共实体。要共享这些对象，需要在指定人口区域只有一个模拟者生成，登记请求含 `cell_id`、生成租约版本和幂等生成键，服务器批量分配实体 ID；其他客户端关闭该区域相应单机生成或将其限制为不可交互的背景。进入同一区域、NPC 车辆的乘客及任务依赖必须随同一个一致包移交。只共享随机种子无法保证各客户端人口完全相同。

## 协议版本、序号与事件

引入新的 `world_v2` 能力和明确 `schema_version`，先保留现有 v1 玩家协议兼容入口，由服务器转换到同一注册表。不能让 v1 与 v2 分别维护两份世界事实。

每个服务器进程维护 `world_tick` 与 `world_revision`；每次提交实体事务增加世界版本和对应实体 `revision`。客户端输入使用独立 `input_seq`，服务端确认结果含 `ack_input_seq`。服务器只接受绑定 session 的 sender，并为每次所有权转移增加 `owner_epoch`，即使旧 socket 上的消息晚到也不能继续控制对象。

客户端更新提议可以采用统一信封：

```json
{
  "type": "entity_input",
  "schema_version": 2,
  "world_epoch": "e3",
  "entity_id": "w:e3:81",
  "owner_epoch": 4,
  "input_seq": 512,
  "based_on_revision": 19,
  "component": "transform",
  "value": {"position": [712.0, -1088.1, 22.4], "velocity": [2.0, 0.0, 0.0]}
}
```

`based_on_revision` 用于判定需不需要纠正，不能要求每个高频移动包都精确等于最新版本而误拒并发合法输入。创建、入座、死亡、换所有者等重要事务则要求对应版本前置条件，服务器提交后回执。一次命中修改受害者血量、击杀与死亡计数，应作为同一个服务器事务，不能让字段分别被旧快照覆盖。

确认事件的共同信封含 `world_epoch`、`world_tick`、`world_revision`、`event_id`、实体 ID、实体版本和相关组件。受害者或伤害量来自服务端判定；输入中的瞄准点不直接等于命中对象。暂未支持的组件、近战、爆炸或车辆伤害明确拒绝，不能因用了通用 `event` 字段就接受未经验证的客户端结果。

客户端必须按世界 epoch、实体 revision 和 generation 拒绝旧结果；死亡／重生／删除不能只根据本机 native health 或 ragdoll 推断。显示副本如果独立受伤或倒地，应根据权威状态修复。渲染用的枪声、轨迹或动作不能产生第二次实际伤害。

## 加入快照与增量恢复

加入步骤必须保证快照和之后事件属于同一连续世界：

1. 完成身份和资源版本协商，服务器确定初始兴趣区域。
2. 在世界更新锁或单写入循环内取一个一致切面 `cut_revision`，开始缓存该连接后续相关事件。
3. 分块发送实体、组件、所有者和删除记录，均使用同一 `snapshot_id` 与切面。
4. 发送 `snapshot_end`，客户端原子替换相应逻辑基线，再按版本应用切面之后缓存的事件。
5. 资源加载成功后报告 `entity_ready`；未加载时仍保存逻辑实体并发心跳，不能把模型加载失败当成世界实体删除。

```json
{
  "type": "snapshot_begin",
  "schema_version": 2,
  "world_epoch": "e3",
  "snapshot_id": "s102",
  "cut_revision": 18000,
  "world_tick": 2450,
  "cells": ["2:-5", "3:-5"]
}
```

世界版本是全局提交号，但一个客户端并不会订阅所有实体，因此不能仅凭 `world_revision` 不连续就判定丢包。每条连接另外维护连续 `stream_seq`，客户端用它和快照确认号发现自身分发缺口；合并高频姿态时显式声明新的基线。可靠生命周期事件不得静默丢弃。

删除保留带 generation／revision 的短期 tombstone，直至相关客户端确认或恢复窗口结束。重连可在同一 world epoch 且事件窗口足够时补发 delta；否则重新发送一致快照。原来的 60 秒身份恢复和新的世界恢复必须分开：保留身份不意味着可以重用断线前的仿真租约。

## 断线与所有权迁移

Java 仍是公共战局协调者，不需要选举新的房间服务器。需要迁移的是客户端代算的实体与区域：

1. 连接无有效应用消息达到当前 30 秒超时，立即释放 socket；关键实体仿真租约应更短，不能等待整个恢复期才发现车辆没人更新。
2. 服务器撤销旧租约并增加 `owner_epoch`，最后确认状态继续保留。没有接手者时先冻结动态仿真，不删除车辆或把它重置到初始位置。
3. 按资源就绪、距离、延迟和负载选择可见且可信的候选模拟者。驾驶员仍在线时优先由驾驶员模拟车辆；NPC 区域可转给另一名已载入该区玩家。
4. 候选者收到冻结基线和新 epoch，创建／接管 native 实体、恢复姿态及任务并确认 ready 后，服务器才激活新租约。
5. 旧玩家六十秒内恢复时仍保留原身份与计分，但必须接受当前世界所有权；不得凭旧 token 抢回已移交的车辆。

移交动态任务的具体内容需要采样支持。不能序列化的 NPC 内部 AI 状态，应明确采用受控重新规划，不能声称无损迁移。车辆乘客与附件要与主体同时重建，否则会出现两个驾驶员、悬空乘客或挂接到错误句柄。

## 兴趣订阅与流式加载

服务端空间索引根据其确认的玩家坐标计算兴趣集合，而不是照单全收客户端任意订阅位置。起步可用固定网格，按距离分层订阅近处完整动态实体、远处低频概况，进出范围采用滞回，避免边界反复创建删除。

`scope_enter` 包含该实体的完整基线；`scope_leave` 只卸载本地副本，不删除世界实体。实体实际删除必须另发 `entity_delete`。车辆、乘客、挂接物及正在交互目标构成依赖集合，随主体一起订阅；交火目标和相关伤害接收者不应因单个边界判断被漏发。小地图玩家概况可以使用独立低频频道，无需为一个远处标记创建完整 ped。

模型、贴图和地图资源仍由 GTA 的 streaming 层按画面需要加载；网络兴趣范围与资源加载范围是两套机制。WebRTC DataChannel 可以作为未来动态状态传输优化，但不会负责“镜头走到哪加载到哪”，也不会自动统一地图或实体。现有 WebSocket 可继续作为第一阶段的可靠传输，先完善语义、拥塞合并及快照，再按真实带宽和延迟决定是否增设另一条状态传输。

高频 transform 状态允许在发送前合并为最新版本；创建、删除、座位、租约和战斗事务必须可靠且有顺序。队列过载时先降低动态频率并请求基线恢复，仍无法维持的连接才断开；不能一直积压旧姿态导致客户端看到很久以前的世界。

## 原网络层复用的独立研究线

最值得继续研究的是原 `netObject`、同步树、对象控制迁移和实体 scope，它们已经表达了不同 GTA 实体的专属状态。若能可靠恢复原网络管理器，复用这层比长期为每种原生任务逐条手写动画更接近游戏本身的行为。

但该路线需要独立完成至少三项证明：

- 恢复 `netSocket` 的创建、发送、非阻塞接收、关闭和线程唤醒，或用具有相同返回语义的浏览器桥替代。
- 在自有会话流程中建立有效 peer、网络管理器和网络脚本 handler，验证原 native 不再访问空上下文。
- 两端用同一构建完成一个原生 net ped 与一个原生 net vehicle 的创建、状态交换及控制权迁移，并查清对象序列化与身份属性。

Java 网关只转发原二进制包时仍是网关，不能因此声明它掌握了 AI 或物理。也不能用当前 JSON 世界协议冒充原 GTA Online 协议。本文没有推断 ROS 票据可以省略或替换，没有访问官方身份服务。该研究线与自有统一世界协议并行，但必须先有实测证据再选择切换，不能一次性启用所有网络线程期待自动恢复。

## 可落实的改造顺序

| 阶段 | 完整交付目标 | 一致性与安全约束 |
| --- | --- | --- |
| 统一世界内核 | 单写入世界循环、实体注册表、类型化组件、统一版本、删除记录和快照；现有玩家协议转换到相同状态 | 双向状态与重生一致；乱序／旧版本不复活实体；重连恢复不重复创建 |
| 首个共享车辆 | 一辆服务器登记的车辆、模型／姿态／速度、驾驶位和乘客事务、仿真租约 | 两客户端认同同一辆车；同时抢座只成功一方；换司机和断线迁移不复制车辆 |
| 区域人口 | 指定 GTA 引擎客户端运行该区 NPC／交通，批量登记与 scope，其他客户端抑制重复生成 | 同路段NPC与车辆一致；区域交接和晚加入得到相同存活对象；无人区冻结可恢复 |
| 战斗与交互统一 | 玩家和NPC共享combat组件，采样／应用与权威判定分离；以验证过的能力逐步覆盖交互 | 两端血量与死亡一致；视觉不独立扣血；每种支持交互有可观察回执 |
| 仿真权威提升／原网络复用 | 选择已验证的原对象同步路径，或提供服务器碰撞与仿真运行时 | 遮挡、碰撞、AI 和迁移由各自适配层处理；不采用原 GTA Online 协议 |

统一内核是整体改造的起点，随后按完整对象类型推进，而不是继续只加孤立的“射击”“踢人”事件。每个阶段都复用同一 ID、租约和快照机制。当前 Java 可以立即承担这套协调架构；逼近完整 GTA Online 的难点仍是引擎实体仿真、原网络运行条件和真实客户端一致性，不能靠外部服务端接口数量解决。
