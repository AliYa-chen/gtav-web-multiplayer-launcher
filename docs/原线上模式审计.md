# 原线上模式与私服复用审计

审计日期：2026-10-07。只读取当前 `game.wasm` 的 type、import、function、code、export、name 节、相关静态字符串以及 `game.js`、`loader.js`、`index.html`。没有运行原游戏，没有修改 WASM，没有连接官方服务。

## 结论

该构建保留了大量原网络会话、玩家、实体同步和线上脚本命令，值得进一步研发复用；但当前文件不能通过“去掉禁用网络参数、填 Java 服务器 IP”就进入原线上模式。除了缺少浏览器调用桥，原生网络适配存在明确的空实现，浏览器 socket 胶水也有功能缺口，原身份、票据和匹配服务的协议仍在。因此，当前新写的 Java WebSocket 大厅不能被当成原 GTA Online 私服。

缺少 export 本身不证明无法实现：补导出或重编能让内部函数变成调用入口，但不会自动补齐 socket、会话身份、线程调度、协议、实体归属和生命周期。下列证据明确区分了“代码还在”“适配能工作”“协议兼容”这三个问题。

## 浏览器 socket 胶水与协议差异

`game.js` 压缩代码主要位于第 1 行；以下定位使用 **0 起字符偏移**和可搜索符号，避免把字符偏移误当成字节偏移。

- `SOCKFS` 从字符 61368 开始：`createSocket` 只接受 `family == 2`；接受 stream/datagram 类型，但都使用 `websocket_sock_ops`。这不是浏览器直接访问原生 TCP/UDP。
- `createPeer` 附近从字符 63561 开始：默认 URL 构造成 `ws://地址:端口/`，请求 `binary` WebSocket 子协议，并设置 `binaryType="arraybuffer"`。datagram 模式还会发送 10 字节 `FF FF FF FF "port" 高字节 低字节` 握手消息。这与新大厅的 `/ws` 文本 JSON v1 协议不同。
- `SOCKFS.websocket_sock_ops.listen` 明确为 `if (!ENVIRONMENT_IS_NODE) throw new FS.ErrnoError(138)`；浏览器环境不能监听原生端口。`accept` 还要求已有 server 和 pending 队列。
- `___syscall_setsockopt` 从字符 89838 开始：验证 fd 后固定返回 `-50`；没有落实设置选项。`___syscall_shutdown` 紧随其后：固定返回 `-52`。
- `___syscall_getsockopt` 从字符 81854 开始：仅 `level === 1 && optname === 4` 有实现，其它返回 `-50`。
- `___syscall_socket/connect/recvfrom/sendto` 的封装确实存在，并把 pthread 请求代理到引擎主线程。这些符号的存在不能弥补上面的空实现，也不能让 JSON 大厅自动理解引擎的原始网络包。

上面的错误号是该胶水实际使用的数值，不应拿 Linux 系统上的相同数字直接解读。

当前 WASM 的相关实际 import 包括函数索引 69 `__syscall_poll`、76 `__syscall_accept4`、77 `__syscall_connect`、79 `__syscall_getsockopt`、80 `__syscall_recvfrom`、81 `__syscall_sendto`、82 `__syscall_setsockopt`、84 `__syscall_socket`，均来自 `env`。JS 虽也定义 bind/listen 适配，当前 import 节没有导入它们。未找到专门的 `wasm_net` 桥。不能据此推断所有 TCP/UDP 调用点已经被完整迁移。

## 可行的工程方向与验证标准

复用原网络逻辑需要恢复或替换 `netSocket` 本机适配，建立适合浏览器的传输（WebSocket 中继或 WebRTC），并定义自己的会话身份、匹配和游戏启动流程。若继续复用原二进制包，还需厘清原会话描述、对象序列化、控制权迁移和版本兼容。这个工作量明显高于写房间列表服务。

重编或补导出可形成调用桥，不能跳过运行时条件：函数必须在正确的引擎线程、TLS、游戏状态和帧调度点执行；对象可能涉及网络管理器、模型预载、脚本线程和持有锁。角色/载具句柄必须随进出局、重生、断线和重新载入更新，不能跨不同客户端复用同一数值句柄。若把页内回调直接放进错误线程，可能造成越界或实体状态损坏。

另一个方向是先复用单机实体命令做独立同步层，逐步验证角色生成与位置、伤害/死亡、载具归属和座位。该方向仍需引擎桥，不能只增加若干 JSON 字段就宣布可玩。

本次静态审计定位了 Java 大厅的连接、房间和通知协议。

## 补充：Send / Receive 与可复用边界

进一步按指令边界解析了下列函数体中的直接 `call` 和 `call_indirect`，没有把常量字节里的 `0x10` 误当作调用指令。这里只追已列出的函数和具体 libc 调用点，不声称重建了完整的原联机协议。

| 函数 / 索引 | 函数体偏移 / 字节数 | 实际证据 |
| --- | --- | --- |
| `rage::netSocket::Send(...)` / 13571 | 7633632 / 624 | 没有 `send`、`sendto`、syscall 或间接调用。直接调用只有计时、`IsReadyToSend()`、格式化/日志、临界区和 `SizeofPacket()`。余下指令做有效句柄检查及流量统计，不能发送原 payload。 |
| `rage::netSocket::Receive(...)` / 13829 | 7839343 / 3110 | 没有 `recv`、`recvfrom` 或对应 import。原接收路径在 7840045 执行 `i32.const -1` 并存 result，7840049 的 `i32.const 1; br_if 0` 恒跳过该块；仍保留延迟/模拟接收队列、日志和统计。唯一间接调用在 7842365，是循环内的 packet-recorder 回调，不是原生接收调用。 |
| `rage::netSocket::SetInitialValues()` / 13817 | 7830131 / 428 | 7830247–7830249 把对象偏移 8 的 handle 初始化为 -1；同时清理对象内部队列及状态。没有 socket 创建调用。 |
| `rage::netSocket::netSocket()` / 13938 | 7886822 / 307 | 构造临界区后调用 `SetInitialValues()`，没有创建网络连接。 |
| `rage::netSocket::Select(...)` / 13828 | 7838614 / 727 | 调用 libc `select`（90916），这部分等待/检查逻辑仍保留。 |
| `rage::netSocket::IsReadyToSend() const` / 13831 | 7843043 / 257 | 调用 `select`，但就绪检查本身不会补齐 Send 中缺失的发送操作。 |

所以，单改 `NativeBind` 或把对象的 handle 手工改为正数也不足以恢复传输：`Send` 和原接收入口仍缺少真实 I/O。

另外，POSIX socket 胶水确有其它用途，不能把整个程序都描述成“没有网络代码”：

- `rage::netTcp::ConnectFd(...)`（13738，偏移 7785063，1021 字节）直接调用 `socket`（91106）、import `__syscall_getsockopt`（79）和 import `__syscall_connect`（77）。
- libc `recvfrom`（91101）直接调用 import 80；其直接调用者是 `EmbedReceiveFrom`（90690）和 libc `recv`（91100）。`EmbedReceiveFrom` 还调用 `wolfSSL_dtls_get_using_nonblock` 和 `setsockopt`。
- libc `sendto`（91103）直接调用 import 81；其直接调用者是 `EmbedSendTo`（90691）和 libc `send`（91102）。
- import `__syscall_socket`（84）的直接调用者是 libc `socket`（91106）；该 wrapper 的直接调用者为上述 `netTcp::ConnectFd`。

这些现存 TCP/TLS/DTLS 路径与被替换为空实现的 `netSocket` 游戏 peer 传输属于不同调用链。

若尽量复用游戏原包，最低需要补齐：创建/绑定及地址分配、原始包发送、非阻塞接收（含来源地址）、等待/就绪和错误语义、接收队列长度、关闭及线程唤醒。入口需要按真实 `netSocketAddress`、内存指针、长度和返回码 ABI 实现，并保留包整形、锁与事件通知。当前 JS 的 datagram 仅是 WebSocket 封装，不提供 UDP 网络；要用它就需要支持 `binary` 子协议和其 `port` 握手的网关，也可以另写明确的新传输适配。

网关即使能转发原二进制包，也只是传输层：还必须在原会话层建立 `rlGamerInfo`、`rlSessionInfo`、peer 地址与身份映射，以及双方所需的密钥/会话属性。`rlSession::CmdHost::Update()`（14528）实际调用 `netPeerAddress::GetLocalPeerAddress`（13603）、`rlCreateUUID`（14296）、`rlSession::Data::Validate`（14504）、`netP2pCrypt::Key::~Key`（13645）及 `rlScMatchmaking::Advertise`（14510）。这说明原会话对象不等于当前大厅的六位房间码。本审计没有实现或伪造 ROS 票据服务，也没有证明这些属性可省略。

## 补充：网络实体 native 不是独立的免会话入口

可定位 `CommandNetworkRegisterEntityAsNetworked(int)`（54900，偏移 31685333，166 字节）、`CommandNetworkGetNetworkIdFromEntity(int)`（54896）、`CommandNetworkGetEntityFromNetworkId(int)`（54897）以及 `CommandSetNetworkIdCanMigrate(int,bool)`（55006）、`CommandSetNetworkIdExistsOnAllMachines(int,bool)`（55007）。它们仍可作为未来原网络实体层复用线索，但不是“给实体写一个统一 ID 就自动联机”的 API。

54900 先获取游戏实体 guid，调用 `CNetObjObject::CanBeNetworked`（86895）及 `NetworkInterface::RegisterObject`（82999）；后者最终调用 `CNetworkObjectMgr::RegisterGameObject`（86746）。54896 检查实体是否注册到当前脚本线程；54897 从当前 `CGameScriptHandler` 查脚本实体再创建本地 guid。55006/55007 还依赖当前 `CGameScriptHandlerNetwork`、网络组件状态和对象扩展，并含虚调用。没有已建立的网络管理器和网络脚本环境时，不能把这些 native 当成单机独立同步入口。

原建房 native `CommandNetworkHostSession`（54639）先调用 `CheckMultiplayerAccess`（54628），才调用 `NetworkInterface::HostSession`（83078）。54628 实际检查多人角色 slot、cloud load pending、`CNetwork::CanAccessNetworkFeatures`（82943）和 `CNetworkSession::CanEnterMultiplayer`（85869）。这证明存在会话/访问条件；不等于每个网络实体 native 都直接发起 ROS 请求。

为了尽可能复用而保持实验可控，可先在正常游戏脚本线程中验证已有实体创建/查询命令，完成双客户端实体证明；同时把原 peer 传输恢复作为独立阶段。单机实体同步层可以使用自有身份与会话，但它应被准确称为自有同步层，不应被标记为已兼容原 GTA Online 协议。
